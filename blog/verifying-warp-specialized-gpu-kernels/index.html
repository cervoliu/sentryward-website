SentryWard: Formal Verification of Warp-Specialized GPU Kernels

Warp-specialized GPU kernels overlap data movement, matrix multiplication, and output processing by assigning different roles to warps within a thread block. On Hopper and Blackwell GPUs, these roles interact with asynchronous copy engines and tensor cores. An instruction can return before the operation it initiates has completed, so program order alone does not establish when operands or results are ready.

Correctness therefore requires both a concurrency argument and a computation argument. Synchronization must order conflicting memory accesses and resource lifetimes; the resulting computation must implement the intended tensor function. A missing completion wait can violate the first requirement even when numerical tests pass, while an indexing or layout error can violate the second in a race-free kernel.

SentryWard is a static verifier for NVIDIA PTX that addresses these requirements in three stages: certification of barrier-phase assignments, race and resource-lifetime analysis, and equivalence checking against a PyTorch reference. This article develops the method through a Blackwell matrix-multiplication example, examines findings in three kernel libraries, and reports synchronization-removal results for 44 kernels at two input sizes.

Verification scope and assumptions

A verification instance specifies the kernel’s PTX, input metadata and parameter values, a launch configuration, and any configured modeling assumptions. A PyTorch reference and a binding between reference and kernel inputs and outputs are needed for equivalence checking. The guarantees below apply to that instance and to executions admitted by the selected model.

  • Fixed shapes and launch configuration. A proof does not automatically extend to other problem sizes, thread-block dimensions, or pipeline configurations.
  • Static control flow. The analysis presented here requires branch outcomes and loop bounds to be determined without reading tensor data. Explicit assumptions that select data-dependent paths further restrict the scope of a result.
  • Immediate memory visibility. The model separates asynchronous issue from execution and completion, but assumes that a memory effect becomes visible when it executes. It does not model fences or the full PTX weak-memory semantics.
  • Real-arithmetic equivalence. Floating-point values are interpreted as real numbers. Equivalence establishes equality of the modeled functions, not bitwise equality under floating-point rounding.

These are conditional guarantees: their applicability depends on the supplied configuration, the configured assumptions, and the accuracy of the hardware model. An unsupported operation, an exhausted analysis budget, or a failed equivalence proof is not a successful verification result. In particular, failure to prove equivalence is not itself a counterexample.

Execution model and running example

In a warp-specialized kernel, different warps perform different roles. The Tensor Memory Accelerator (TMA) transfers input tiles, while tensor cores execute matrix multiply-accumulate (MMA) operations. Both operate asynchronously. A block-wide barrier such as __syncthreads() coordinates participating threads, but is not by itself a completion wait for these TMA and tcgen05 operations. The roles instead communicate through mbarriers: shared-memory objects whose phases track pending arrivals and outstanding transaction bytes. A phase completes when both counts reach zero. NVIDIA’s PTX specification describes these barrier operations.

The running example computes one \(128 \times N\) tile of \(C = AB\) from a \(128 \times K\) tile of \(A\) and a \(K \times N\) tile of \(B\). A full kernel iterates over tiles of the reduction dimension and reuses its shared-memory buffers; the example shows one iteration. There are 128 threads: thread 0 issues the input copies, thread 32 issues the MMA, and all 128 threads participate in the epilogue. The barrier full signals that both input tiles are available in shared memory; mma_done signals that the accumulator is available in tensor memory. For the illustrated transfers, each input tile occupies 16 KB.

The following pseudocode isolates the synchronization dependencies. It abstracts allocation, descriptors, physical data layouts, and instruction-specific participation requirements; it is not executable PTX.

// 128 threads (4 warps), thread index t.
if t == 0:
    init(full, 1)
    init(mma_done, 1)
syncthreads()

if t == 0:                           // producer
    arrive.expect_tx(full, 32 KB)        1
    tma_load(sA ← A, full)               2 3
    tma_load(sB ← B, full)               2 3

if t == 32:                          // MMA issuer
    wait(full, 0)                        4
    tcgen05.mma(acc ← sA * sB)           5
    tcgen05.commit(mma_done)             6

wait(mma_done, 0)                    // epilogue 7
r = tcgen05.ld(acc[t, :])                8
tcgen05.wait::ld()
st.global(C[t, :] ← r)                   8

The relevant producer-consumer dependencies are explicit: step 4 orders the MMA after the input copies, and step 7 orders the epilogue’s tensor-memory loads after the MMA. The subsequent tcgen05.wait::ld() waits for those loads before their register results are stored to global memory.

A schedule-dependent data race

Consider a variant that omits the epilogue’s wait at step 7:

wait(mma_done, 0)                    // epilogue (buggy)
r = tcgen05.ld(acc[t, :])
tcgen05.wait::ld()
st.global(C[t, :] ← r)

The barrier updates are unchanged: the input copies complete phase 0 of full, and the MMA commit supplies the arrival that completes phase 0 of mma_done. However, no dependency orders the epilogue’s loads after the MMA. The two schedules in Figure 2 differ in whether the accumulator is read before or after the tensor core writes it.

The missing dependency is apparent in this example. In a pipelined implementation, the corresponding producer and consumer may be separated by several roles, stages, and asynchronous operations. The CUTLASS case study below examines a related publication of data before an asynchronous store is known to have completed.

Numerical tests and dynamic race detection examine executed paths and schedules. They provide empirical evidence, but do not establish that every admitted schedule is safe. SentryWard instead seeks a static ordering argument that covers those schedules without enumerating them.

Verification method

The analysis has three proof obligations. First, each barrier update and wait must have a schedule-independent phase assignment. Second, conflicting memory accesses and resource uses must satisfy the required ordering constraints. Third, when a reference is supplied, the modeled outputs must equal the reference outputs in real arithmetic. The first property is well-synchronization, introduced for named barriers by WEFT and extended here to mbarriers. Each stage relies on the preceding guarantees. Diagnostics identify failed obligations, such as a pair of potentially conflicting accesses without a proved ordering; incomplete analyses are reported separately.

Program representation

SentryWard first specializes the PTX for the supplied configuration. For the static-control fragment considered here, it resolves branches and unrolls control-flow loops to obtain finite instruction sequences. It then constructs two complementary representations: an event view of ordering and memory effects, and a value view of the expressions loaded, stored, and computed. Immediate effects are represented by events at the instruction; asynchronous operations have distinct issue and execution events. Program-order edges capture the dependencies imposed by each thread’s instruction sequence.

Synchronization analysis

Program order provides intra-thread constraints; barriers provide inter-thread dependencies. An mbarrier advances through a sequence of phases. Within a phase, arrive reduces the pending-arrival count, expect_tx increases the expected transaction count, and completion of a tracked TMA transfer reduces that count by the transferred bytes. When both counts reach zero, the phase completes and the counters are reset for the next phase. The shorthand wait(bar, parity) represents a wait for completion of a phase identified by its parity.

A wait observes completion of a particular phase, but the schedule may affect which updates contribute to that phase. An update executed before phase 0 completes contributes to phase 0; the same update executed after completion contributes to phase 1. Well-synchronization requires that every barrier update and wait be assigned to the same phase in every admitted execution. This is a verification restriction rather than a necessary condition for every correct concurrent program. It matches the intended phase discipline of many pipelined kernels, in which wait parity is derived from the loop iteration.

Following WEFT, SentryWard constructs a candidate phase assignment from one terminating trace. It records the phase of each update and wait, then builds a candidate graph with a completion vertex for each phase. The trace supplies the candidate; it is not itself a proof about other schedules. Certification establishes that all admitted schedules respect the assignment. For named barriers, WEFT checks that an update is ordered after completion of the preceding phase. Successful certification yields a happens-before graph whose ordering constraints hold across executions, and establishes deadlock freedom under the model.

The transaction-byte counter introduces an additional obligation. A named barrier counts only arrivals, so a phase cannot complete before its final arrival. Transaction counts can both increase and decrease. Consequently, a phase can reach zero pending arrivals and zero pending bytes before all updates assigned to it in the candidate trace have executed. Remaining updates then contribute to a later phase. For example, consider a producer that announces the two 16 KB transfers separately:

if t == 0:                           // producer (another bug)
    arrive.expect_tx(full, 16 KB)
    tma_load(sA ← A, full)
    expect_tx(full, 16 KB)
    tma_load(sB ← B, full)

If copy A completes before the second announcement, phase 0 completes and the second announcement contributes to phase 1. This differs from the missing-wait example: the candidate phase assignment itself is schedule-dependent. SentryWard therefore checks whether a dependency-respecting, proper subset of a phase’s updates can bring both counters to zero. Such a subset witnesses premature completion; here it consists of the first announcement and completion of copy A.

The separate-announcement variant is both not well-synchronized and unsafe under the model: if copy A completes first, the MMA can read sB before copy B writes it. In general, however, a failed well-synchronization check identifies a violation of the verifier’s phase discipline, not necessarily an incorrect output.

The missing-wait variant passes phase certification because its barrier updates retain their original phase assignments. It fails the next obligation: its happens-before graph contains no path from MMA execution to the epilogue’s loads (Figure 5). This separates phase consistency from race freedom.

Race freedom and serialization

Race analysis checks reachability in the certified happens-before graph. Two memory accesses conflict when their byte footprints may overlap and at least one is a write. For each pair \((a,b)\) treated as conflicting by the selected model, the required condition is

\[a \prec_{\mathrm{HB}} b \quad \lor \quad b \prec_{\mathrm{HB}} a.\]

Access footprints account for the physical layout, including swizzled shared-memory tiles. When addresses are symbolic, an SMT solver is used to reason about overlap. An unordered conflicting pair is reported as a race candidate; an unresolved query cannot establish race freedom.

In the missing-wait variant, MMA execution and the epilogue’s accumulator loads are unordered, so the report identifies those accesses as the race witness. Resource-lifetime checks use the same ordering machinery: a use of tensor memory, for example, must precede its deallocation.

The certified ordering permits sequential reasoning about the modeled computation. For an input within the verified domain, the remaining analysis can choose a serialization consistent with the happens-before graph. Under the checked ordering and modeling assumptions, this preserves the memory effects relevant to the outputs across admitted concurrent executions.

Compact representation

An explicit per-thread, per-scalar representation does not scale: a block has hundreds of threads, and a single \(128 \times 256\) output tile with \(K = 4096\) involves about \(1.3 \times 10^8\) multiply-accumulates. Most of this size comes from repetition. SentryWard therefore represents each family of repeated threads, data elements, or reduction steps by a single indexed template, and analyzes the templates directly. A thread template covers a group of threads that have taken the same branches.

Reductions are represented in the same way. Instead of a chain of operations, a Fold stores a reduction by its operator \(\oplus\), its index range, its initial value \(z\), and the term \(e(k)\) at each index:

\[\mathit{Fold}_{\oplus}\bigl(k \in [l, n),\ z,\ e(k)\bigr) = z \oplus e(l) \oplus e(l+1) \oplus \cdots \oplus e(n-1).\]

Its size does not depend on the length of the range. In the running example, the MMA computes each element of its accumulator as

\[\texttt{acc}[t, j] = \mathit{Fold}_{+}\bigl(k \in [0, K),\ 0,\ \texttt{sA}[t, k] \cdot \texttt{sB}[k, j]\bigr).\]

SentryWard builds Folds from MMA instructions and from repeated updates in the code; memory elimination and the expression check then work on them directly, without unrolling them.

Equivalence checking

Well-synchronization and race freedom do not establish functional correctness: an indexing error, an incorrect layout, or a missing scale factor can remain. Once concurrency checks justify serialization, SentryWard applies memory elimination to obtain expressions over the inputs, then checks those expressions against the PyTorch reference.

Memory elimination

Memory elimination follows the serialization and keeps a memory state: the expression last stored at each address. Each store updates the state at its address, and each load is replaced by the expression that the state holds at its address, or by an input if nothing was stored there. The buffers in between, here sA, sB, and acc, drop out, and each output element becomes an expression built only from the inputs.

Expression checking

The expression check takes two pure expressions over the same inputs: the kernel’s, from memory elimination, and the reference’s. They are rarely identical, because an optimized kernel computes its reductions differently from the reference: it may split a reduction into parts, combine the parts in a different order, or rescale them. To prove the two expressions equal, SentryWard uses the reference as a guide: it relates the kernel’s expression, part by part, to the reference’s intermediate results.

Figure 10 shows an example: attention for one query \(q\) and four keys of dimension four, with a scalar value \(v_j\) for each key \(j\). The reference computes the scores \(s_j\), the sum \(Z\) of their exponentials, and the weighted sum \(U\) (a sum is a Fold with \(\oplus = +\) and \(z = 0\)). The optimized kernel splits each score between two threads, one for the even \(k\) and one for the odd \(k\). It processes the keys in two blocks with online softmax: within a block, it subtracts the block’s largest score before taking exponentials, and the merge rescales both blocks to the overall largest score \(m\). To show that the kernel’s output \(p / \ell\) equals \(U / Z\), SentryWard proves five equalities, in order.

At each step, SentryWard decomposes a kernel expression as \(c \cdot \sum_{k \in S} t(k) + r\), where \(t(k)\) matches terms of a reference reduction, \(c\) is a common factor, and \(r\) is the residual expression. When \(S\) covers the reference index domain exactly once, the matched sum can be replaced by the reference reduction; the factor \(c\) and residual \(r\) remain. Coverage is checked using a compact representation of index sets based on generating functions, rather than explicit enumeration. This supports large and strided ranges. Reduction-free expressions are compared by canonicalization into exponential polynomials, with separate treatment of operations such as square roots.

Figure 10 uses two blocks to expose the proof structure. For supported kernels that merge blocks in a loop, SentryWard uses induction with an invariant relating the loop state to the reference. This capability is limited to predefined patterns, including online softmax and Welford statistics; the tool does not synthesize arbitrary loop invariants.

The result is a proof in real arithmetic, subject to the input domain and modeling assumptions. Reordering a reduction may still change floating-point rounding on hardware. The equivalence procedure is also incomplete: equivalence_not_proven records an unproved obligation, not a demonstrated numerical error.

Evaluation

Case studies and evidence

The following case studies distinguish a previously confirmed defect from two reported ordering concerns. The PyTorch example was fixed independently upstream. The TileLang issue and CUTLASS pull request remain open as of 14 October 2026; their reports do not establish a reproduced hardware failure for the patterns discussed here.

The concurrency findings depend on SentryWard’s interpretation of the PTX execution rules. Missing ordering in the event model is evidence for a potential defect, but hardware may provide behavior not captured by that model. Conversely, failure to reproduce a problem in testing does not establish safety across all schedules. We therefore report static findings, hardware observations, and upstream confirmation separately.

PyTorch: an independently confirmed missing barrier. In PyTorch 2.8.0, the MultiMarginLoss backward kernel distributes a row of gradients across a thread block. Thread 0 writes the target-class gradient; each thread then scales the entries it owns. Without a barrier between these operations, another thread can scale the target entry before thread 0 writes it. SentryWard identifies this unordered pair. The defect was independently reported and fixed upstream; the barrier is present in PyTorch 2.9.0. This case validates detection of a known defect rather than constituting a new discovery.

// one block per row; thread t owns columns t, t + blockDim, ...
for each of my columns i ≠ target:
    gradInput[i] = h(i)                   // 0 if the margin holds
    buffer[t] -= h(i)
__syncthreads()
if t == 0:
    gradInput[target] = sum(buffer)       // thread 0 writes the target entry
__syncthreads()                           // missing; PyTorch 2.9.0 adds it
for each of my columns i:
    gradInput[i] *= gradOutput            // the owner of target scales it

TileLang: a potential shared-memory stage-lifetime violation. In the reported TileLang v0.1.15 pipeline, tiles \(k\) and \(k+2\) share a buffer. The generated code issues the next copies into that buffer after issuing the MMA for tile \(k\), but before waiting for its completion. Because the MMA reads its operands asynchronously, issue order alone does not establish that the reads finish before the buffer is overwritten. SentryWard reports a potentially conflicting copy write and MMA read. The report documents the generated ordering and a static race candidate; its numerical hardware check could not be run.

# TileLang program
for k in T.Pipelined(num_tiles, num_stages=2):
    T.copy(A[k], A_shared)
    T.copy(B[k], B_shared)
    T.tcgen05_gemm(A_shared, B_shared, C_tmem, mbar=mbar)
    T.mbarrier_wait_parity(mbar, k % 2)

// generated loop body, iteration k, stage s = k % 2
tcgen05.mma(acc += sA[s] * sB[s])         // the tensor core reads stage s
tcgen05.commit(mbar)
__syncthreads()                           // does not wait for the tensor core
// the copies of tile k + 2 overwrite stage s
cp.async(sA[s] ← A[k + 2])
cp.async(sB[s] ← B[k + 2])
wait(mbar, k % 2)                         // MMA k is known to be done only here

CUTLASS: a potentially premature statistics notification. In the Blackwell attention example, the softmax warpgroup writes row statistics to tensor memory and signals the correction warpgroup. The analyzed path has no tcgen05.wait::st between the asynchronous store and the signal. Under SentryWard’s model, the signal therefore does not establish that the statistics are available before the consumer loads them. The proposed upstream fix and investigation document the missing wait in compiled code, but also report that B200 stress tests did not reproduce stale reads. Whether an additional hardware guarantee makes the existing sequence safe remains unresolved.

// softmax warpgroup, once per tile of keys
tcgen05.st(stats ← old_max, new_max)
tcgen05.wait::st()                        // missing
arrive(stats_ready)                       // tells the correction warpgroup
...
tcgen05.st(P ← probabilities)
tcgen05.wait::st()                        // here the kernel does wait
arrive(p_ready)                           // tells the MMA warp

// correction warpgroup
wait(stats_ready, phase)
r = tcgen05.ld(stats)                     // not ordered after the store in the model
scale = exp(r.old_max - r.new_max)

Removing redundant synchronization

Synchronization removal tests whether an ordering operation is necessary for the checked properties at a particular configuration. Starting from a kernel that passes synchronization and memory checks, we remove one candidate operation, rerun those checks, and retain the removal only if they still pass. Candidates are considered greedily, so the retained set depends on the removal order; the procedure does not claim a globally minimal synchronization set.

Experimental setup. The reported evaluation compares 44 kernels at two input sizes: the example inputs and larger inputs selected to exercise reuse of every pipeline buffer. The reduced kernels are evaluated on a B200. Runtime reduction is measured relative to the original kernel at the same input size:

\[\text{runtime reduction (\%)} = 100\,\frac{t_{\mathrm{original}} - t_{\mathrm{reduced}}}{t_{\mathrm{original}}}.\]

Positive values indicate lower runtime; negative values indicate a regression. Figure 14 shows all 44 per-kernel measurements, including kernels with no measurable improvement.

Input dependence. Larger inputs permit fewer removals in this cohort. Applying the reductions obtained at the example inputs to the larger inputs causes SentryWard to reject 35 of the 44 reduced kernels; 34 of those rejected variants hang or fault on B200. Thus, a removal justified for one configuration must be reverified for another.

Numerical validation. For the reductions accepted at each input size, random testing produced outputs identical to the original kernels over 500,000 launches at the example inputs and 20,000 at the larger inputs. These observations complement the static synchronization and memory checks; they do not establish bitwise equivalence for untested inputs.

Limitations and future work

  • Symbolic input shapes. Extending specialization and phase reasoning to symbolic dimensions could allow one proof to cover a specified family of shapes and launches.
  • Data-dependent control flow. Reasoning about tensor-dependent branches and loop bounds would extend coverage beyond the static-control fragment, without relying on assumptions that select representative paths.
  • Weak-memory semantics. Modeling visibility, fences, and memory-ordering scopes is needed to replace the immediate-visibility assumption with a more complete account of PTX execution.
  • Floating-point semantics. Modeling rounding, overflow, and reduction order would support numerical guarantees beyond real-arithmetic equivalence, including error bounds for low-precision kernels.

The present method separates phase consistency, memory safety, and functional equivalence into explicit proof obligations. Its conclusions should be interpreted together with the verified input domain, modeling assumptions, and evidence reported for each check.
